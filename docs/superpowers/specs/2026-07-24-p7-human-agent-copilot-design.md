# P7 人工客服与 AI 副驾设计

## 1. 目标

P7 在 P4 会话实时通信、P5 AI 编排和 P6 售后闭环基础上，建立从 AI 服务转人工、技能组排队、自动分配、客服接管、实时沟通、转派到 AI 副驾的完整协作链路。

阶段出口：会话可以按技能组正确分配；客服接管后 AI 不再向消费者公开发言；人工消息可实时到达消费者；客服能够查看、采纳、修改或忽略 AI 建议；主管能够处理异常占用和强制转派。

## 2. 范围

### 2.1 本阶段实现

- 技能组、技能标签、客服成员关系、数据范围和最大接待量。
- 客服在线状态、忙碌状态、当前接待量和容量校验。
- 规则化队列优先级、自动分配、限时邀请、拒绝、超时重分配和主动领取。
- 客服接管、人工实时消息、转技能组、转指定客服、结束接待和关闭会话。
- 主管查看本租户全部队列、强制转派和释放异常占用。
- 用户新消息触发私有 AI 副驾建议，客服可手动刷新、采纳、修改发送或忽略。
- AI 建议及修改差异审计，记录模型、Prompt 和工作流版本，不保存模型思维链。
- `aliagent-admin` 最小客服工作台：队列、会话接管、实时聊天、转派、结束、AI 建议及处理动作。

### 2.2 本阶段不实现

- 主管技能组配置页面和完整运营后台。
- 客服绩效、质检看板和实时大屏。
- P8 持续评测、发布门禁和评测集管理。
- 真实工单系统和完整离线工单流转。
- AI 自动执行取消、退款、审批等业务写操作。
- 新建独立人工客服微服务。

## 3. 架构决策

采用 `conversation-service` 中心化方案：

- `conversation-service` 是人工客服协作事实来源，负责技能组、队列、优先级、分配邀请、接管、转派、容量、人工消息和主管干预。
- `ai-orchestration-service` 负责生成私有副驾建议，通过受控只读工具访问知识、订单、物流和售后状态，不拥有队列或会话分配事实。
- `frontend/aliagent-admin` 提供最小客服工作台，通过 Gateway 调用 REST，并复用 P4 WebSocket 实时通道。
- Gateway 继续移除客户端伪造的内部身份头，注入可信租户、主体、角色、权限、`traceId` 和 `requestId`。
- 跨服务调用必须同时验证短期服务 JWT 和用户身份快照。

不新建独立 `agent-service`，避免 P7 引入额外数据库、跨服务事务和实时状态同步成本。

## 4. 领域模型

### 4.1 技能组

技能组至少包含：

- `skillGroupId`
- `tenantId`
- `code`
- `name`
- `enabled`
- `dataScope`
- `maxQueueSize`
- `assignmentTimeoutSeconds`
- `priorityRuleVersion`

技能标签与技能组多对多关联。客服成员关系记录客服在技能组中的技能、启用状态和最大并发接待量。技能组、标签和成员关系通过数据库及受保护 API 管理，P7 不提供主管配置页面。

### 4.2 客服状态

客服状态沿用并明确以下语义：

- `OFFLINE`：不可参与自动分配或领取。
- `ONLINE`：可参与自动分配和主动领取。
- `BUSY`：在线但达到容量或由客服主动设置，不参与新分配。

当前接待量以未结束的有效接管记录为准，不能只依赖 Redis 计数。Redis 可用于在线心跳和快速路由，PostgreSQL 保存可恢复事实。

### 4.3 会话人工状态

- `AI_ACTIVE`：AI 可以公开回复消费者。
- `WAITING_HUMAN`：进入人工队列，AI 不得公开回复。
- `ASSIGNING`：存在有效分配邀请，AI 不得公开回复。
- `HUMAN_ACTIVE`：客服已接受接管，只有人工消息可公开发送；AI 只作为私有副驾。
- `CLOSED`：会话已显式关闭，不再排队或接收普通消息。

普通结束人工接待后恢复 `AI_ACTIVE`；只有客服明确选择关闭会话时才进入 `CLOSED`。

### 4.4 队列与邀请

队列项记录目标技能组、路由标签、优先级分数、规则版本、入队时间、尝试次数和当前状态。分配邀请记录候选客服、过期时间和接受结果。

关键约束：

- 一个会话同一时间最多有一个有效队列项。
- 一个会话同一时间最多有一个有效分配邀请。
- 一个会话同一时间最多有一个有效接管记录。
- 接受邀请、主动领取、转派和结束操作必须使用幂等键。
- 接受邀请时必须在同一事务内校验邀请有效性、客服状态、技能和容量，并创建接管事实。

### 4.5 AI 副驾建议

副驾建议至少记录：

- `suggestionId`
- `tenantId`
- `conversationId`
- `triggerMessageId`
- `assignedAgentId`
- `content`
- `status`
- `modelVersion`
- `promptVersion`
- `workflowVersion`
- `citations`
- `createdAt`

处理记录保存 `ACCEPTED`、`MODIFIED`、`IGNORED` 或 `REFRESHED`，并记录原始建议、最终发送内容和差异摘要。原始建议始终是 `PRIVATE`，只有客服确认发送后才创建 `STAFF/PUBLIC` 消息。

## 5. 核心流程

### 5.1 转人工和自动分配

1. 用户主动请求人工，或 AI/业务规则产生转人工请求。
2. 系统根据意图、类目、售后类型和租户配置生成候选技能标签。
3. 确定性规则选择技能组，并按冻结的规则版本计算优先级。
4. 会话进入 `WAITING_HUMAN`，创建唯一队列项。
5. 分配器在匹配技能的 `ONLINE` 客服中，按当前接待量由低到高选择候选人。
6. 系统创建限时邀请，会话进入 `ASSIGNING`。
7. 客服接受后原子校验容量并进入 `HUMAN_ACTIVE`；拒绝或超时则重新分配。
8. 达到最大自动分配次数后，队列项转为可主动领取，并向主管暴露升级标记。

AI 可以提供意图和路由标签，但最终技能组、优先级和分配结果必须由确定性规则决定。

### 5.2 队列优先级

优先级规则按版本保存，并在入队时固定。排序因素按以下顺序组合：

1. 高风险售后、投诉和敏感承诺风险。
2. 等待时长。
3. 会员等级。
4. 同优先级下按入队时间先进先出。

重试、超时和服务重启不得使用新规则重新解释既有队列项。AI 不参与最终优先级裁决。

### 5.3 接管和公开消息

客服接受邀请或主动领取成功后：

- 会话进入 `HUMAN_ACTIVE`。
- AI 编排在生成公开内容前必须查询或消费会话控制状态；非 `AI_ACTIVE` 时禁止公开流式回写。
- 用户消息继续持久化并通过 WebSocket 推送给当前客服。
- 客服消息使用 `clientMessageId` 保证幂等，持久化成功后才实时推送消费者。
- Redis 故障时，消息事实仍可从 PostgreSQL 查询和恢复。

### 5.4 转派

支持两种转派：

- 转技能组：结束当前接管占用，创建指向新技能组的队列项，重新自动分配。
- 转指定客服：校验同租户、目标技能、在线状态和剩余容量后，创建限时转派邀请；目标接受后才切换接管关系。

转派未完成前原客服保持会话责任，避免无人负责。主管可以强制转派，但仍必须满足租户边界和审计要求。

### 5.5 结束与关闭

- 普通结束：关闭当前接管记录、释放容量，会话恢复 `AI_ACTIVE`。
- 显式关闭：关闭接管记录和队列项，会话进入 `CLOSED`。
- 主管释放异常占用：仅用于过期心跳、断连或数据不一致场景，必须记录原因和操作者。

### 5.6 AI 副驾

在 `HUMAN_ACTIVE` 状态收到新的用户消息后自动触发副驾建议。客服可以手动刷新，但同一触发消息和工作流版本必须具备幂等控制。

副驾可使用：

- 当前对话历史与摘要。
- P3 知识检索及引用。
- P5 订单、物流只读工具。
- P6 售后申请、审批、退款和补偿状态只读查询。

副驾不得：

- 直接向消费者公开回复。
- 直接调用取消、退款或审批写操作。
- 把模型生成内容持久化为订单、物流、退款或审批事实。
- 保存或展示模型思维链。

## 6. 实时事件

需要定义并版本化以下事件或等价内部消息：

- `conversation.human.requested`
- `conversation.queue.entered`
- `conversation.assignment.offered`
- `conversation.assignment.accepted`
- `conversation.assignment.rejected`
- `conversation.assignment.expired`
- `conversation.transferred`
- `conversation.human.released`
- `conversation.human.closed`
- `conversation.staff.message.created`
- `copilot.suggestion.requested`
- `copilot.suggestion.generated`
- `copilot.suggestion.actioned`

事件统一使用平台事件信封。跨服务写入使用 Outbox，消费者使用 Inbox 或消费记录幂等。WebSocket 通知不是业务事实来源，丢失后必须能通过 REST 或消息序列恢复。

## 7. API 边界

### 7.1 管理配置 API

仅 `SUPERVISOR` 或具备相应权限的管理主体可以：

- 创建、修改、启停技能组。
- 维护技能标签。
- 维护客服成员关系和最大接待量。
- 查看本租户全量队列。

### 7.2 客服操作 API

`STAFF` 可以：

- 更新在线状态。
- 查看自己所属技能组队列。
- 接受或拒绝分配邀请。
- 主动领取开放队列项。
- 发送人工消息。
- 转技能组或发起指定客服转派。
- 结束人工接待或显式关闭会话。
- 查看、刷新、采纳、修改或忽略副驾建议。

### 7.3 主管操作 API

`SUPERVISOR` 可以：

- 查看本租户全部技能组队列和分配状态。
- 强制转派会话。
- 释放异常占用。

所有接口必须从可信请求上下文取得 `tenantId` 和主体，不接受客户端提交的租户作为授权依据。

## 8. 最小客服工作台

`frontend/aliagent-admin` 增加最小客服工作台，包含：

- 我的邀请和待接队列。
- 已接管会话列表。
- 会话历史和实时人工聊天。
- 用户、订单、物流和售后只读摘要。
- 转技能组、转指定客服、结束和关闭操作。
- AI 副驾建议、引用、刷新、采纳、编辑发送和忽略操作。
- 当前在线状态、接待量和最大容量。

前端只展示服务端授权后的数据，不在浏览器计算最终队列优先级或分配结果。所有高风险操作必须处理重复点击和过期状态。

## 9. 一致性、并发与恢复

- 队列入队、邀请接受、主动领取和转派使用数据库唯一约束与事务锁防止双接管。
- 客服容量在创建或释放有效接管事实时原子更新或实时计算。
- 分配器可以多实例运行，但同一个队列项只能被一个实例成功认领。
- 邀请过期由可重入调度任务扫描，重复执行不得产生多个新邀请。
- 在线状态允许 Redis 加速，但服务重启后必须基于心跳过期规则恢复为 `OFFLINE`。
- AI 建议生成失败不能阻塞人工聊天；只返回可重试状态。
- 模型、知识服务或 mall 只读接口故障时，建议不得虚构业务事实。

## 10. 安全与审计

- MEMBER 只能查看自己的会话和公开消息。
- STAFF 只能访问本租户且在其技能组或当前分配范围内的会话。
- SUPERVISOR 只能干预本租户会话。
- 指定客服转派必须校验目标客服同租户、技能匹配、在线和容量。
- 客服状态变化、队列变更、邀请处理、接管、转派、释放、关闭和副驾操作全部记录审计。
- 日志和审计不得保存服务 JWT、完整敏感凭证或模型思维链。
- 副驾原始建议和最终发送内容按平台数据保留策略处理，为 P8 提供匿名化候选样本，但 P7 不执行评测集发布。

## 11. 任务拆分与目录所有权

### P7-A：技能组、队列、分配与主管能力

负责 `conversation-service` 中新的 `agent`、`skill`、`queue`、`assignment` 领域目录及对应测试。交付技能组 API、成员和容量、优先级规则、自动分配、限时邀请、主动领取和主管干预核心。

### P7-B：接管、转派与实时人工消息

负责 `conversation-service` 中新的 `handoff`、`takeover`、`transfer`、`staffmessage` 领域目录及对应测试。扩展 P4 状态与 WebSocket 行为，保证人工接管互斥、转派安全、消息幂等和恢复。

### P7-C：AI 副驾与最小客服工作台

负责 `ai-orchestration-service` 中新的 `copilot` 目录、对应测试，以及 `frontend/aliagent-admin` 的客服工作台页面与专属前端模块。交付私有建议、受控只读上下文、版本审计、采纳修改差异和最小 UI。

### 集成会话唯一负责

- 公共 OpenAPI、AsyncAPI 和 JSON Schema。
- conversation-service 公共 Flyway 迁移及 Bean 装配。
- 根 POM、公共配置、Gateway 路由、Compose 和 CI。
- 跨任务共享模型冲突、跨服务事件连接和完整端到端测试。

三个实施任务从同一冻结提交创建独立分支和 Worktree，禁止修改其他任务拥有的目录或相互合并。

## 12. 验收标准

- 会话按技能标签进入正确技能组，并使用冻结规则版本计算优先级。
- 自动分配按技能、在线状态和当前接待量选择客服。
- 邀请接受后才进入 `HUMAN_ACTIVE`；拒绝或超时会重新分配，最终可主动领取。
- 并发接受、主动领取或转派不会产生双接管或超容量。
- 转人工后 AI 不再公开发言，人工结束并恢复 `AI_ACTIVE` 后 AI 才可重新公开回复。
- 客服人工消息实时到达消费者，重复 `clientMessageId` 不重复持久化。
- 转技能组和转指定客服均通过租户、技能、在线和容量校验。
- 主管可查看本租户全部队列、强制转派和释放异常占用，跨租户操作被拒绝。
- 用户新消息自动生成私有副驾建议，客服可刷新、采纳、修改发送或忽略。
- 副驾建议包含知识引用和实时业务事实；依赖故障时不虚构订单、物流、退款或审批结论。
- 保存原始建议、最终内容、操作结果和版本信息，不保存思维链。
- 双实例、Redis 故障、MQ 重投、邀请过期扫描和服务重启恢复场景通过。
- 所有测试数据使用 `test-` 或 `rag-test-` 前缀，并在端到端测试后清理。

## 13. 已确认决策

- 实现最小可用客服工作台，不实现完整主管配置和绩效页面。
- 自动分配优先，超时后允许主动领取。
- 技能组配置使用数据库和受保护 API。
- 自动分配需要客服限时确认，拒绝或超时后重分配。
- 队列优先级使用版本化确定性规则，AI 不作最终裁决。
- 支持转技能组和指定客服。
- 普通结束恢复 AI，显式操作才关闭会话。
- 提供最小主管查看、强制转派和异常释放能力。
- AI 副驾自动生成并支持手动刷新，只使用受控只读工具和 RAG。
- 保存建议与客服修改差异及模型、Prompt、工作流版本，不保存模型思维链。
