# P8 持久化与发布验签集成设计

## 目标

将 P8 从事件摄入局部持久化推进为可发布验收的闭环：候选审核、不可变数据集、回放结果、Gate Decision 和撤销均由 `evaluation_db` 保存；P5 与知识发布通过受服务 JWT 保护的 evaluation-service 验签接口进行实际校验。

## 边界与原则

- `evaluation-service` 是评测、门禁证明和撤销状态的唯一事实来源；其他服务不直写 `evaluation_db`。
- 每个租户表、读取条件、唯一约束均绑定 `tenant_id`。公共数据使用固定平台租户，不允许空租户。
- 事件原文只在匿名化调用栈中存在。数据库、日志、证明和前端只处理匿名内容、摘要和状态。
- 发布、灰度和知识发布必须获得与目标租户、类型、版本、清单摘要、策略匹配且未过期、未撤销的 `PASS` 证明；验签服务不可用默认拒绝。
- 回滚已发布旧版本仍使用独立审计路径，不接受借回滚发布新版本。

## 持久化模型

新增 V3 迁移补足 V2 的业务字段：候选审核的期望结果/标签/审计差异，数据集草稿组成与版本样本快照，回放清单、任务状态、样本结果和指标证据，DashScope 审批与预算账本，门禁策略、证明规范化载荷、签名和撤销记录。

每个领域由专用 JDBC 仓储负责。数据库 profile 下 Spring 仅装配 JDBC 实现；非数据库 profile 的内存实现只用于单元测试。所有写操作依赖数据库唯一约束实现幂等，应用层只将重复写映射为已有事实。

## 内部验签协议

evaluation-service 提供受服务 JWT 保护的内部验签端点。请求携带目标租户、制品类型、制品版本、清单摘要、策略版本和 Gate Proof；响应仅包含 `accepted` 与拒绝分类，绝不返回签名私钥或敏感评测内容。

P5 与 knowledge-service 的 `GateDecisionPort`/`KnowledgeGateDecisionPort` 使用该端点。客户端必须同时验证调用响应中的 `accepted=true`；网络、5xx、格式错误和超时均转为拒绝。P5 的 `PROMPT`、`WORKFLOW`、`MODEL` 发布与租户灰度，知识版本发布与灰度均走相同目标绑定校验。

## Gateway 与权限

Gateway 为 `/api/v1/evaluation/**` 注入可信身份、服务 JWT、traceId 和 requestId，并删除客户端伪造的内部头。evaluation-service 从可信头取得租户和主体，不从请求体授权。候选审核、数据集和任务仅允许评测管理员；证明签发、版本发布入口仅允许版本管理员；DashScope 审批与公共共享要求独立管理员权限。

## 端到端流程

1. 版本化事件进入 Inbox，完成匿名化后创建候选。
2. 管理员审核候选，形成带期望结果与标签的已接受样本。
3. 已接受样本进入草稿；发布时复制为不可变版本和样本快照。
4. Mock 回放固定数据集版本与版本清单，持久化任务、结果、指标证据和结果摘要；基线与候选仅在同条件下比较。
5. 门禁以结果、策略和红线生成 `PASS` 或 `FAIL`；仅 PASS 可签发并持久化证明，撤销后立即失效。
6. 管理员显式提交证明执行 P5 或知识发布/灰度；evaluation-service 不自动发布。

## 验收与清理

每个 JDBC 仓储有临时 PostgreSQL schema 集成测试。完整 E2E 使用 `test-p8-` 前缀，覆盖重复事件、敏感信息不落库、跨租户拒绝、不可变数据集、Mock 可重复、红线 FAIL、伪造/过期/撤销证明拒绝，以及有效 PASS 后的显式发布。

验收结束后删除临时 schema/数据库、`test-p8-` Redis 键和 RabbitMQ 测试队列；记录清理前后数量。Compose 使用只在进程内生效的验收变量，不写入仓库 `.env`。
